# Spotify 同步逻辑优化研究

## 1. 用户的设想
将 30s 轮询的 `now-playing` API 与 10分钟一次的 `sync` Worker 联动：如果当前没有在听歌，Worker 就跳过请求 `recently-played` 数据，从而减少请求次数。

## 2. 核心漏洞分析

这种联动在理论上似乎能减少请求，但在实际架构和业务逻辑中存在三个致命缺陷：

### 缺陷一：观察者效应 (无访客时停止更新)
30s 一次的 `/api/now-playing` 请求是由**前端 (客户端) 的 SWR 发起的**（见 `SpotifyProvider.tsx`）。
这意味着，**只有当有人打开你的网站并停留在页面上时，这 30s 的轮询才会发生**。如果你在上下班路上用手机听歌，且此时没有任何人访问你的网站，`/api/now-playing` 是**永远不会被触发**的。
如果让 Worker 依赖 `now-playing` 的状态，那么当你网站没有访客时，你的听歌历史将彻底停止同步，丢失所有数据。

### 缺陷二：尾随歌曲丢失 (Trailing Song Problem)
假设我们解决了上面的问题（比如通过后端主动轮询），依然存在业务逻辑漏洞。
当你听完最后一首歌，或者手动点击“暂停”时，Spotify 才会将这首歌推入 `recently-played` 历史列表中。此时，`now-playing` 接口返回的是 `isPlaying: false`。
如果 Worker 在 5 分钟后触发，发现 `isPlaying` 为空，于是**跳过**了拉取 `recently-played`，那么你听的最后一首歌将永远无法被同步（直到你下次重新开始听歌并恰好跨过下一个 Worker 触发周期）。
因此，不能仅仅因为当前没有听歌就不拉取最近播放，至少需要有一个“冷却期”（例如：确认已经连续 20 分钟没有听歌，才可跳过）。

### 缺陷三：并没有真正减少 API 请求数
在现有的架构下，如果我们在 `/api/spotify/sync` 内部先调用 `getCurrentPlayback()`（判断是否在听歌），如果为空再 return。
虽然你跳过了拉取 `recently-played` 的请求，但你依然向 Spotify 发起了 1 次 `getCurrentPlayback()` 请求。
一来一回，Spotify API 的请求次数还是 1 次，并没有减少。同时，Vercel 的 Serverless Function 依然被唤醒了一次，Vercel 计算资源也没有节省。

## 3. 正确的优化逻辑是什么？

基于上述分析，**不推荐将 30s 的前端轮询与后端持久化 Worker 联动**。10分钟一次的请求每天仅产生 144 次 Spotify API 调用，远低于 Spotify 的速率限制，且 Vercel 的调用次数也在免费额度内。

如果极度渴望优化，正确的逻辑应该是**基于最后更新时间（Last Active Time）的自适应轮询 / 冷却机制**：

1. **维持现状独立性**：30s 轮询仅为前端 UI 动画和状态服务，10m Worker 专职为后台历史记录归档服务。两者解耦。
2. **在 Worker 或 Sync API 中增加“跳过逻辑”**：
   - 每次请求 `recently-played` 时，记录返回数据中最新一首歌的 `played_at` 时间戳，将其视为 `last_active_time`。
   - 当 Worker 触发时，首先判断当前时间距离 `last_active_time` 过去了多久。
   - 如果发现已经超过了 24 小时没有任何新歌（说明用户今天没听歌），可以将 10 分钟的频次通过代码逻辑自动“降级”（例如直接 return，或者改成每小时才真正发起一次 Spotify 请求）。
   - **注意**：必须确保冷却期大于 10 分钟，以防止“缺陷二”中提到的最后一首歌未被收录的情况。

## 结论
目前的 10分钟 Cron 策略是**最稳妥、最不漏数据**的方案。
联动的想法会因为**前端轮询的间歇性**和**歌曲播放结束后的延迟结算**导致数据丢失。建议保持 Worker 的独立运行。
